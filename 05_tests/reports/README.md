# Test Reports

One directory per test run, written by
`05_tests/infra/scripts/run-all-tests.sh`.

```
reports/
├── RUN_20260910_005338/
│   ├── TEST_REPORT.md      Terminal-friendly summary
│   └── TEST_REPORT.html    Self-contained, for handing to someone else
├── RUN_.../
└── TEST_REPORT_2026-07-22_18-53-19.md    Legacy: pre-RUN_ flat files
```

Both files describe the same run and carry the same title,
`Trillian · Driving Coach v<version> — Test Report`.

## The HTML report

Generated by `generate-html-report.py`. It answers one question for a reader who
has never seen this project: *how is this software tested, and how much of it is
actually covered?*

It is self-contained — no JavaScript, no external stylesheets, nothing fetched
over a network — so it opens from a USB stick in a paddock with no signal.

Sections, in order. Evidence comes before interpretation: the reader sees the
failures and every test that ran before any claim is made about what they cover.

| # | Section | What it shows |
|---|---------|---------------|
| 1 | Results by test level | Declared vs executed per ASPICE level |
| 2 | How we test | What each level can and cannot prove |
| 3 | Failures | Every failure in full |
| 4 | Every automated test in this run | The complete inventory |
| 5 | Manual acceptance tests (L4) | The checks only a human can discharge |
| 6 | Requirements coverage | Which test claims which requirement |
| 7 | Gaps and caveats | What is not covered, and what is deferred |

### Why it counts tests twice

Gradle reports a class annotated with a class-level `@Ignore` as a *single*
skipped entry, no matter how many tests it contains. A suite can therefore look
green while dozens of tests never run.

So the report counts `@Test` in the Kotlin source as well as reading the JUnit
XML, and shows both numbers. The gap between them is the point: it is how 29
switched-off L2 tests were found. See `FP-TEST-BLINDSPOT` in
`SkunkOps/atlas/failure-patterns.md`.

## Inputs

Everything the report states comes from structured input. No prose is parsed
anywhere, so it cannot mis-read a document and overstate coverage.

| Input | Supplies |
|-------|----------|
| `app/build/test-results/testDebugUnitTest/*.xml` | L1 outcomes |
| `app/build/outputs/androidTest-results/connected/debug/*.xml` | L2 outcomes |
| `app/src/{test,androidTest}/**/*.kt` | Declared `@Test` counts, class-level `@Ignore` |
| `05_tests/coverage-map.tsv` | Which test claims which requirement |
| `01_requirements/DrivingCoach_SRS_v1.md` | The requirement denominator |
| `05_tests/scope-map.tsv` | What V1 defers to a V2 backend |
| `05_tests/L4_SYS5_acceptance/*.md` | Manual checks |

## Generating

```bash
# Run tests, write a RUN_ directory, then offer to package a release
./05_tests/infra/scripts/run-all-tests.sh --start-emulator --stop-emulator

# Regenerate the HTML from results already on disk
python3 05_tests/infra/scripts/generate-html-report.py --output /tmp/report.html

# Byte-reproducible output, for diffing two runs
python3 05_tests/infra/scripts/generate-html-report.py --source-date "2026-01-01"
```

## What is committed

`RUN_<timestamp>/` directories **are** tracked, so the evidence for a given
commit stays with it. The legacy flat `TEST_REPORT_*.md` files are matched by
`.gitignore`, though the ones committed before that rule was added remain
tracked — git does not retroactively ignore a file it is already following.

Release copies live in `releases/v<version>-<slug>/` next to the APK they
describe, so a build and its evidence cannot be separated. That directory is
gitignored: it holds binaries.

---

*The report is the only artefact allowed to state coverage. If it disagrees with
a hand-written table, the report is right — it is generated from the tests
themselves.*
